# mtqgの使い方（このリポジトリの運用）

作業の中で生まれる「気づき・やること・質問と答え・不具合とそのやり取り・用語の合意・この先も効き続ける決まり事」を、コードと同じgitリポジトリの中に追記だけで残すツール。使い方の詳細は`mtqg`自身の`.mtqg/SCHEMA.md`（データ形式）と`mtqg --help`（コマンド）を見る。

このリポジトリは、mtqg（`github.com/amisonnet8/mtqg`）を使って開発の過程を記録する。mtqg自身はこのリポジトリのコードではなく、`.devcontainer/postCreate.sh`が`go install .../mtqg/cmd/mtqg@latest`で入れるバイナリをPATH越しに使う（mtqgがv1タグを公開したため、2026-09-29にコミット固定から`@latest`へ変更した）。VS Code拡張（`amisonnet8.mtqg`）は`devcontainer.json`の`extensions`から入る。

**進捗管理の文書（PLAN.md相当）はこのリポジトリに無い**（`CLAUDE.md`「記録の使い分け」）。すべてmtqgの記録から拾う。

## 記録者

`.claude/settings.json`の`env`に`MTQG_AUTHOR_KIND=ai`・`MTQG_AUTHOR_NAME=claude-code`を設定済み。コマンドの前に明示しなくても、このリポジトリでのmtqgコマンドは記録者`ai`/`claude-code`になる。人間が記録するときだけ、`.claude/settings.json`の値を上書きするよう明示して呼ぶ（例：`MTQG_AUTHOR_KIND=human MTQG_AUTHOR_NAME=<名前> mtqg r add "..."`）。

## 何をどの種類で記録するか

| 種類 | 例 |
|---|---|
| `m add`（memo） | 実装しながらの気づき、後で見返したい観察。**不具合はここに書かない**（下の`b add`を見る） |
| `t add`（todo） | やること。**着手前に立てる**（「後でまとめて」にしない。小さな作業でもよい）。**終わったら間を置かず`t done`にする**（開いたままにしない） |
| `q add`（question） | 判断に迷って人間に確認したいこと。**設計や実装に関わる質問は、聞き方（チャットでの一言、`AskUserQuestion`、プランモード中の確認など）を問わず必ず`q add`で記録する。** `AskUserQuestion`で人間に聞いたときは、その場で質問と回答を`q add <id> <回答>`まで記録する |
| `b add`（bug） | 見つけた不具合とそのやり取り。**判定基準：「本来動くべきものが動いていなかった」「仕様と実装がずれていた」はbug、単なる気づき・設計判断はmemo。** その場で直したものも含めて記録する（**「直したから」は判定基準に入らない**）。優先度・担当者・再現手順の欄は無い（課題管理はしない） |
| `g add`（glossary） | 用語の合意（`//`、qsokufile、居場所の持ち帰り、など） |
| `r add`（rule） | 読めばそのまま従える決まり事。`.claude/rules/*.md`は、このruleの記録から人間が選んで書き写す派生文書という位置づけ（mtqg本体`docs/design/history.md`2026-09-25） |

- **記録は日本語で書く**（`mtqg rule` `75cb5c8eb0`「mtqgには日本語で登録する」、2026-09-27）。以前は「英語・日本語どちらでもよい」としていたが、セッションの後半で記録言語が英語に寄ってしまった気づき（memo `bedb693497`）を踏まえ、ruleとして明文化した。mtqgは中身を訳さない・変えない仕様なので、これはmtqg側の制約ではなくこのリポジトリでの申し合わせ。過去の英語の記録はそのまま残す（書き換えない）
- IDは4桁以上の前方一致で指定できる（`mtqg show <ID先頭4桁以上>`）

**`memo`と`bug`の境目（2026-09-23、人間に指摘されて整理）：** qsoku自身のコード・スクリプトの**欠陥**は、同じセッション内ですぐ直した場合でも`b add`→直した内容を`b add <id> <返信>`→`b done`で記録する。「もう直したから」と`memo`で済ませない。`memo`は、外部ツール（zsh・fish等）の挙動の発見、設計判断の理由、テスト環境固有の事情など、**qsoku自身の欠陥ではないもの**に使う。迷ったら「これはqsokuのコードが間違っていたのか、それとも前提や外部の挙動の話か」で判断する

## このPJと関係のないことは記録しない

**このPJの`.mtqg/`には、このPJの作業だけを記録する。** 同じコンテナ・同じ会話で頼まれた、別のPJ・別のリポジトリ・道具そのものの作業は、このPJの記録に混ぜない。混ぜると、`mtqg context`がこのPJの現状を示さなくなり、人間もAIも作業を取り違える。

- 例：このPJのAIが、別のPJ（srwr・テンプレート・ほかの兄弟PJ）の修正や調査を頼まれたとき。その作業の記録は、**そのPJ自身の`.mtqg/`**（`cd`してから`mtqg`を動かす）に書く。記録先が無い・迷うときは、記録せずに会話で報告する
- 例：このPJが使う道具（qsoku・mtqg・srwr・golangci-lint）の不具合を見つけたとき。このPJの動作に影響する範囲（回避策・版の注意）だけを、このPJに`m add`する。道具そのものの不具合の追跡は、道具のリポジトリで行う
- 記録する前に確かめる：**「このPJのコード・文書・設定・決まり事の話か」**。違えば、このPJには書かない
- コミットも同じ。別のPJの変更を、このPJのコミットに混ぜない（`git add`はパスを指定する）

## 作業を始めるとき

- **必ず`mtqg context`を読む。** 現在地・未完了のtodo・未回答の質問・未解決のbugがここに出る。`SessionStart`フックがセッション開始・再開のたびに自動でこれを読み込むが、圧縮後の再開などで見えていないと感じたら、手で`mtqg context`を読み直すこと
- まだ`.mtqg/`が無ければ、`mtqg init`を一度実行し、案内に従って`.mtqg/`をコミットする

## こまめに記録する

**`mtqg context`だけで、このリポジトリの現状と次にやることが分かる状態を保つ。**

- **todoは着手前に立て、終わったらすぐ`t done`にする。** まとめて書く・まとめて閉じる、をしない。開いたままのtodoは「今も残っている作業」として信用されるので、終わったのに開いたままだと現状を誤らせる
- **区切り（1つの変更、1つの決定、1つの確認が付いたところ）ごとに、その場で`m add`する。** セッションの終わりにまとめて数件書くのではなく、都度書く
- **人間に委ねる判断は`q add`でも開けておく**
- 何を記録すべきか迷ったら、**「これを書かずにセッションが終わったら、次のセッション（または人間）は`mtqg context`だけで気づけるか」**で判断する

## 対話中の質問・回答もその場で記録する

**人間に何か尋ねたら（`AskUserQuestion`でも、地の文の質問でも）、答えを受け取ったその場で記録まで終わらせる。ターンを人間に返さない。** `q add`（質問）→ 答えが来たら `q add <id> <回答>`（「〜との対話で回答、日付」を添える）→ `q done <id>` まで、確認を挟まず続けて実行する。`mtqg q list`で後から質問と回答を振り返れることが目的（2026-09-23、人間の指示。「これがほしかった機能」）。**設計や実装に関わる質問は、聞き方（チャットでの一言・`AskUserQuestion`・プランモード中の確認など）を問わず対象**（`mtqg rule` `c31a05b38d`、2026-09-27。同じ趣旨を明文化したもの）。

- 複数の問いを一度に尋ねた場合は、それぞれを別の記録にする（1問1記録）
- 計画モード中で書き込みができないときは、計画ファイルの手順に「承認直後にまず記録する」と明記し、承認後の最初の作業として実行する
- この扱いは、質問だけでなく人間からの訂正・確認（フィードバックに該当するもの）にも準じる。ただし何を`q`にするかは「判断に迷って確認したこと」に限る（上の表のとおり）。単純な指示や作業依頼は`q`にしない

## 並行して記録する

**設計§12.3（mtqg側の記録）に沿って、少なくとも一度はブランチか別の端末で並行して記録すること。** unionマージと「並行した状態変更」の表示（`mtqg review`）を実地で試すのが、qsokuをサンプルPJにした目的の一つ。

## mtqgの使い勝手についての気づきを残す

**このリポジトリでmtqgを使っていて気づいたことは、その場でmemoかbugに残すこと。** 例：

- コマンドが分かりにくい、表示が足りない、データ形式に欲しいものが無い → memo/bugにして「CLIで直すもの」の候補にする
- AIが記録を忘れる、`context`を読まない、引数を間違える、人間が記録を面倒に感じる → memo/bugにして「MCP・フックで解くもの」の候補にする

開発がひと区切りついたら、これらをmtqg本体のリポジトリへ報告する（2分類の形式は、mtqg本体側の`PLAN.md`「段階2：サンプルPJ」を参照）。

## AIエージェント連携（2026-09-25、`mtqg init --agent claude-code`で配線）

段階3で報告した「MCP・フックで解くもの」3件のうち、Q&Aの自動記録とmemo/bugの一貫性は、mtqg本体側でフック・MCPサーバーとして実装された。qsoku自身にも配線済み。

- **`SessionStart`／`Stop`フック**（`.claude/settings.json`）：セッションの開始・再開時に`mtqg context`の内容を自動で読み込む。終了時、このセッション中にmtqgへの書き込みが1件も無ければ促す。**フックは「読み込みと記録漏れの確認」だけを機械的に行い、何を記録するかの判断はしない**（mtqg本体の設計、役割分担）
- **MCPサーバー**（`.mcp.json`、`mtqg mcp`）：`memo_add`・`todo_add`・`qa_ask`・`qa_answer`・`bug_report`・`bug_reply`・`glossary_define`・`rule_add`・各種`done`/`reopen`・`edit`・`context`・`show`・`search`などが`mcp__mtqg__*`ツールとして直接呼べる。シェルコマンド（`Bash`経由の`mtqg q add`等）を介さずに記録できるため、**「対話中の質問・回答もその場で記録する」（上の節）は、これらのMCPツールで行ってよい**（結果は同じ`journal.jsonl`に書かれる）
- 記録者（`author`）は、MCP経由だと接続したクライアント名から自動で決まり、CLI経由だと環境変数（`MTQG_AUTHOR_KIND`・`MTQG_AUTHOR_NAME`、`.claude/settings.json`の`env`に設定済み）から決まる。どちらでも`claude-code`になる
- `delete`・`undo`・`archive`・`review`・`format`はMCPに公開されていない（破壊的・複雑な操作をAIの判断だけで実行させないため。これらはCLIで行う）

## その他

- `.mtqg/.local/`はコミットされない（マシンごとのロック・一時ファイル）
- `.mtqg/`の中のファイルを直接編集しない（すべてmtqgのコマンド経由）
- mtqgはgitに対して読むだけ（コミット・push・設定の変更をしない）
